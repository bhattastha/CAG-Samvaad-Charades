# RCA — build_image timeout (run 2c755fa2-b0b3-4937-ad51-f53b6f7cecd3)

## Symptom
Initial deploy failed at `build_image`. Cloud Build ended in `TIMEOUT` ("context deadline exceeded"). Both attempts (`6efdab9f-1838-4ebe-8c01-af543383b9c4` and `2c755fa2-b0b3-4937-ad51-f53b6f7cecd3`) died at the exact same place: the `frontend-build` stage, step `[frontend-build 13/14] RUN ... yarn install ... && yarn build`, which printed `Downloading the pnpm 12.15.0 binary for linux-x64...` and then hung (`#52 ...`) until the build clock ran out.

## Root cause — template/project mismatch
The app is NOT the FARM layout this deployment was configured for.

**Deployment template:** `fastapi_react_mongo_shadcn_base_image` (FARM) — a Python-only base image (no Node/pnpm), a single-folder `frontend/` built with `yarn`, and a **MongoDB** backing store.

**Actual app (`hindi-charades`):** a **pnpm monorepo** (`package.json` → `packageManager: pnpm@9.15.0`, `pnpm-workspace.yaml` → `apps/*`, `packages/*`):
- Real backend = `apps/api` (`@hc/api`): **Node.js + Fastify**, run with `tsx`, talking to **PostgreSQL** — `backend/.env` sets `DATABASE_URL=postgres://hc:...@127.0.0.1:5432/hindi_charades` and `apps/api/src/db.ts` opens it with `pg.Pool`.
- Real frontend = `apps/web` (`@hc/web`): **Vite/React**, output `apps/web/dist`.
- `backend/server.py` is only a **FastAPI proxy shim** that forwards all `/api` traffic (HTTP + WS) to `127.0.0.1:3000` (the Fastify API). It contains no application logic.
- Preview works via `scripts/emergent/start.sh`, which apt-installs PostgreSQL, runs `corepack pnpm install`, builds `@hc/web`, and launches the Fastify API with `tsx` on :3000.

### Why the build hangs
In `Dockerfile.cloudbuild`, the `frontend-build` stage does `COPY frontend/ /app/` then `yarn install --prefer-offline ... && yarn build`. But `frontend/` is only a launcher shim:
```
frontend/package.json → "build": "cd .. && corepack pnpm --filter @hc/web build"
```
That build command reaches OUTSIDE the copied `frontend/` directory into the monorepo root (`apps/web`, `packages/shared`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`) — none of which were copied into the stage — and invokes `corepack pnpm`. corepack downloads a pnpm binary and then stalls (no workspace present, non-interactive). The process never exits, so Cloud Build hits its wall-clock TIMEOUT.

## Why this is not a manifest break-fix
Repairing only the frontend build would not produce a working deployment. Two further, deeper blockers remain, and they are outside the 6 deploy-manifest files:
1. **No Node.js runtime** in the FARM base image → the Fastify API (`apps/api`) cannot run, so the Python shim's upstream `127.0.0.1:3000` is never up. `/api` and `/health` (which nginx proxies to the backend) would return 503, failing `deploy`/`health_check`.
2. **No PostgreSQL.** The app requires a Postgres server (`DATABASE_URL=postgres://...@127.0.0.1:5432/...`). This deployment/platform provisions **MongoDB**, not Postgres. A manifest cannot provision a Postgres instance.
Additionally the runtime `entrypoint.sh`/supervisor model starts a single FastAPI `backend` command + nginx; it has no provision to run the Node API on :3000 alongside the Python shim.

## Recommended fix (E1 / Code)
Pick one coherent target:

**Option A — conform the app to the FARM template (Python + React + MongoDB):**
- Make `backend/` a real FastAPI app implementing the API (not a proxy to a Node service), using MongoDB (`MONGO_URL`/`DB_NAME` are the platform-provided system secrets).
- Put a standard single-folder React app in `frontend/` with its own `package.json` + lockfile that builds with `yarn build` to `build/` or `dist/` (no `cd ..`, no pnpm workspace, no corepack).
- Remove the Node/Fastify/PostgreSQL dependency (`apps/api`, `pg`/pglite, `DATABASE_URL`).

**Option B — keep the Node/Fastify + PostgreSQL monorepo:** this requires a deployment stack that supplies a Node runtime and a managed PostgreSQL. The current FARM (Python + Mongo) template cannot host it; deploying it as-is will keep failing at build and then at runtime. This is an infra/stack decision — surface to the user/support if Option A is not acceptable.

## Notes
- `DATABASE_URL`, `JWT_SECRET`, `DHRUVA_API_KEY`, `EMERGENT_EMAIL_KEY`, etc. in `backend/.env` are custom values seeded from preview. The `DATABASE_URL` points at `127.0.0.1:5432`, which will not exist in production regardless.
- No manifest override was written and `resume_pipeline` was NOT called — re-running without a source/architecture change will reproduce the same timeout.
