# RCA — bhashini-game (run 6efdab9f-1838-4ebe-8c01-af543383b9c4)

## Symptom
Initial deploy failed at **build_image**. Cloud Build ended in `TIMEOUT` /
`context deadline exceeded`. The build hung at the `frontend-build` Docker stage,
step `13/14`: `retry_with_backoff yarn install ... && yarn build`.

## Root cause (PROVEN) — project structure does not match the deploy template
This app is deployed with the FARM template `fastapi_react_mongo_shadcn_base_image`
(frontend_type=cloudflare), but the actual project is a **pnpm monorepo running a
Node/Fastify API on PostgreSQL** — not FastAPI + MongoDB + a self-contained React
`frontend/`.

Structure found in the pulled source:
- Root `package.json` → `"packageManager": "pnpm@9.15.0"`, `pnpm-workspace.yaml` →
  `apps/*`, `packages/*`.
- `apps/web` = `@hc/web` (Vite/React), `apps/api` = `@hc/api` (Fastify + `pg`,
  started via `tsx`), `packages/shared` = `@hc/shared` (`workspace:^`).
- `frontend/package.json` is only a shim:
  `"build": "cd .. && corepack pnpm --filter @hc/web build"`.
- `backend/server.py` is only a FastAPI **proxy shim** that forwards `/api`
  (HTTP + WS) to the Fastify API at `127.0.0.1:3000`.

Why the build hangs: the template's `frontend-build` stage runs
`COPY frontend/ /app/` — it copies **only** `frontend/`, not the monorepo. It then
runs `yarn install && yarn build` in `/app`. The shim's `yarn build` does
`cd .. && corepack pnpm --filter @hc/web build`, which executes pnpm from `/`, where
there is no `pnpm-workspace.yaml` and no `@hc/web` package. pnpm with a `--filter`
that matches nothing in a non-workspace directory **hangs indefinitely** → Cloud
Build hits its timeout.

Reproduced in an isolated sandbox on this run's source:
- `pnpm --filter @hc/web build` from `/` (no workspace) → hung the full 60s,
  killed by `timeout` (exit 124). == the Cloud Build hang.
- Same command from the full repo but without `pnpm install` → fails fast:
  `tsc: not found`, `node_modules missing`.
- The build log independently shows the stage downloading the pnpm binary and then
  stalling at `[frontend-build 13/14]` until `TIMEOUT`.

## This is NOT fixable by a manifest edit alone — the runtime is also mismatched
Even if the `frontend-build` stage were rewritten to build the monorepo correctly,
the produced image would not run this app:

1. **Production never starts the real API.** `entrypoint.sh` starts only the
   `[program:backend]` uvicorn process (the FastAPI proxy shim on :8001) + nginx.
   The Fastify API (`apps/api`, the thing the shim proxies to on :3000) is launched
   in *preview* by `[program:frontend] → yarn start → scripts/emergent/start.sh`,
   which production's entrypoint does not invoke. In production every `/api` call
   would get the shim's `503 {"error":"api_starting"}` forever.
2. **No Node runtime / no deps in the final image.** The final image is built on
   the Python `${BACKEND_IMAGE}`; `apps/api` needs Node + `tsx` + its
   `node_modules` (pnpm-installed), none of which the template installs or bakes in.
3. **Wrong database.** The app uses PostgreSQL (`pg`, `start.sh` boots a local
   `postgres`). The pipeline's `provision_mongo` provisions **MongoDB**; the
   platform does not provision PostgreSQL for this template, and `start.sh`'s
   apt-installed Postgres under `/app/.data` is not viable/persistent in k8s.

## Recommended fix
This needs a source/architecture decision by E1 (the main agent); it is not a
deployer manifest tweak:

- **Option A (align app to the template):** Refactor to a genuine FastAPI + MongoDB
  backend under `backend/` with a self-contained React app under `frontend/` (its
  own `package.json` build producing `build/` or `dist/`, no `cd ..` into a pnpm
  workspace). This matches the FARM template and will build and run as-is.
- **Option B (keep the Node/pnpm/Postgres architecture):** This requires a
  Node + PostgreSQL deployment template (build the pnpm workspace, bake Node + the
  Fastify API into the runtime, start it in entrypoint, and a managed Postgres).
  That capability does not exist on the current template — escalate to Emergent
  platform.

No manifest was changed and the pipeline was not re-fired, because no manifest edit
can produce a working deployment given the above.
