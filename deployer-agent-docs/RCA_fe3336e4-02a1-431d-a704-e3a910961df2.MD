# RCA — bhashini-game initial deploy fails at deploy_k8s (pods never become ready)

## Summary
The deploy fails at the `deploy_k8s` step: the new pods never reach Ready and the rollout
times out. Investigation found **two distinct causes**. The first (health-probe path) I fixed
via a manifest override and verified it took effect. The second (a container restart loop driven
by resource exhaustion on the current tier) remains and requires a **user action** — it is not
fixable from the build manifests or app source by the deployer.

Deployment: bhashini-game (a3d40c69-8025-4e6b-8f97-02d53805de8c)
Template: fastapi_react_mongo_shadcn_base_image · frontend_type: cloudflare · tier: tier_0 (Starter)
Runs examined: 9d351ec2 (pre-fix), fe3336e4 (post nginx-fix, force_repull)

---

## Cause #1 — health probe hit an endpoint the app doesn't serve  (FIXED by deployer)

The k8s startup probe hits nginx `location = /health`, which in the stock template proxies to the
backend's bare `/health`. This app's FastAPI shim (`backend/server.py`) only implements
`/api/health` (which has a 180s first-boot "starting" grace that returns HTTP 200). A bare
`/health` falls through the shim's catch-all proxy to the bundled Node API on 127.0.0.1:3000,
which isn't up during first-boot seeding → `ConnectError` → shim returns **503** →
nginx `@health_error` → 503. Run 9d351ec2 showed exactly this:
`GET /health 503 Service Unavailable` (×54) and nginx `connect() failed (111: Connection refused)
... upstream http://127.0.0.1:8001/health`. The failing startup probe killed the container before
the Node API could finish seeding → crash loop.

Fix applied: staged a GCS manifest override of `nginx.conf` changing the health location to
`proxy_pass http://127.0.0.1:8001/api/health;` (plus small timeout bumps to 2s/5s/2s). This routes
the probe to the shim's grace-aware endpoint, which returns 200 "starting" during seeding.
The complete manifest set (config.yaml, Dockerfile, Dockerfile.cloudbuild, entrypoint.sh,
nginx.conf, build-frontend-artifacts.sh) was written in one call; only nginx.conf was changed.
`nginx -t` on the new config passes.

Verification that it took effect: run fe3336e4 (after the fix + force_repull) shows the
`GET /health 503` spam and the nginx upstream `connect() failed` errors are **completely gone**.

## Cause #2 — container restart loop from resource exhaustion on tier_0  (NEEDS USER ACTION)

After the health-path fix, the pods STILL never become ready — the container restart-loops.
Evidence (run fe3336e4):
- Each pod container reports `Started` **6 times** then `BackOff: Back-off restarting failed
  container` — i.e. the container PID1 keeps exiting non-zero, ~every 50–60s.
- App logs show uvicorn cleanly restarting over and over (`Started server process` /
  `Application startup complete`) with **NO Python traceback**, **NO application error**, and
  **NO entrypoint "Backend died / Nginx died" message**. An abrupt non-zero exit with no graceful
  message is the signature of a SIGKILL (OOM-killer / cgroup memory kill), not a code crash.
- Readiness/Liveness probes report `connect: connection refused` on :8080 — a *consequence* of the
  container being down between restarts (nginx not listening), not the root cause.
- This same `BackOff restarting failed container` loop was present in the pre-fix run too, i.e. it
  is independent of the health path.

Why the app is unusually heavy for this tier:
- `get_tier` → tier_0 "Starter": cpu request 50m / **cpu_limit 250m**, memory request 200Mi /
  **memory_limit 512Mi**, 2 replicas. Container image ~1.07 GB.
- The backend runs THREE runtimes inside one 512Mi / 250m container simultaneously:
  1. Python uvicorn (`server:app`),
  2. a bundled Node 22 runtime (`nodejs-wheel-binaries==22.20.0`) executing a 6 MB
     `backend/hc/api.mjs`,
  3. an **embedded PGlite (WASM Postgres) running in-process inside Node**, which seeds sample
     data on first boot (`SEED_PUBLISH_SAMPLES=1`).
- The embedded PGlite path is taken because `DATABASE_URL` points at a preview-local Postgres
  (127.0.0.1:5432) that is unreachable in production; the shim logs
  `DATABASE_URL is not reachable: using embedded PGlite ... Data will NOT survive a redeploy`.

Python + Node + an embedded Postgres + first-boot seeding does not fit in 512Mi, and 250m CPU
makes the WASM seed extremely slow — so the pod is killed before it ever becomes ready, re-seeds,
and loops. (Note: an explicit `OOMKilled`/exit-137 status could not be captured directly because
the failed run's pods were reaped before I could read `last_termination`; the conclusion is from
the kill signature + the tier ceiling + the runtime weight, which have no competing explanation.)

### Recommended fixes for Cause #2 (either or both)
1. **Raise the tier** (Deployment Panel → Resources). tier_0 (512Mi / 250m) is too small for this
   triple-runtime backend; move to at least tier_1 "Launch" (or higher) so the pod has the memory
   and CPU headroom to finish first-boot and stay up.
2. **Point `DATABASE_URL` at a reachable external PostgreSQL** (Deployment Panel → Secrets). This
   stops the pod from running the embedded in-process PGlite Postgres entirely — cutting the
   backend's memory/CPU footprint substantially AND fixing the separate
   "data will NOT survive a redeploy/restart" problem (embedded PGlite is ephemeral). With an
   external DB the app may even fit comfortably at a modest tier.

Optionally, the app team could reduce first-boot cost (e.g. gate `SEED_PUBLISH_SAMPLES`), but the
two actions above are the direct resolution.
